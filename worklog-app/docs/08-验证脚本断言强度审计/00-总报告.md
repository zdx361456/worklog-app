## 二、方法与基线

### 2.1 方法：变异测试

对每条断言，定位它所声称验证的**实现落点**（`文件:行号`），注入**最小破坏**（改常量 / 反转条件 / 换被调函数 / 删分支），重跑脚本：

- **变红** → **真断言** ✓
- **仍绿** → **假覆盖** ✗（须附：断言名 + 注入点 + before→after 逐字 + 重跑输出）

**注入一律在副本内进行，原项目 `worklog-app/**` 全程只读。**
副本方案：复制精简 `app/`（`lib` + `.dart_tool` + `pubspec.*` + 目标 `tool/verify_X.dart`）到 `_scratch/audit-*/appcopy/`。
**可行性依据**（主理人实测确认）：所有 verify 脚本都用**相对路径** `../lib/...` 引项目代码，复制后 `../lib/` 自动指向副本；`package_config.json` 里 `worklog_app -> ../` 亦为相对路径。

### 2.2 运行环境

```bash
DART="D:/workspace/software/installed/tools/FlyEnv-Data/app/flutter/3.47.4/bin/cache/dart-sdk/bin/dart.exe"
export WORKLOG_USE_SYSTEM_SQLITE=1
"$DART" --disable-dart-dev tool/verify_X.dart
```
- **禁用 `dart run`**：会触发 `sqlite3` 包的 native-assets 构建钩子，而本机 Dart VM 的 `Process.start` 全面失效（`CreateFile failed 231 / ERROR_PIPE_BUSY`）→ 必失败。
- `--disable-dart-dev` 跳过 dartdev 直跑 VM；`WORKLOG_USE_SYSTEM_SQLITE=1` 预载 Windows 自带 `winsqlite3.dll`。
- 依赖由 `FLUTTER_ROOT=<flutter> dart pub get --no-precompile` 重建（36 KB）。

## 四、最严重发现（Top 7，均为【实测】）

### ① `verify_db` G3 —— 「唯一不可容忍的方向」出现盲区

**`aggregateByCompany.remaining` 无任何断言。**

```dart
// app/lib/db/database.dart:377
remaining: receivable - received,   →   remaining: received - receivable,
```
**重跑：93 通过 / 0 失败（全绿）**

为何最严重：**P06 公司列表页每行的「剩余」正是取这个值**。符号反转 = 把「还欠我多少」显示成负数，而这是本项目**唯一不可容忍的错误方向**（少算已收 → 剩余虚增）。§6 的 4 条 `aggregateByCompany` 断言**只比 `receivable` / `received`，从不比 `remaining`**。

### ② `verify_waveA` —— 应收下钻接线零覆盖（**用户报的 bug 本体**）

```dart
// app/lib/ui/overview_page.dart:176
filter: RecordsFilter.receivableDrill,   →   filter: RecordsFilter.all,
```
**重跑：54 通过 / 0 失败（全绿）**　（主理人已独立复现）

同类逃逸：`company_detail_page.dart:576` 的 `companyWork(companyId)` 改成 `receivableDrill`（P07 工作 tab 丢公司过滤）、`overview_page.dart:213` 点公司卡片跳错页 → 均双绿。

根因：`verify_waveA` 把「DB 的默认行为」当成「页面接线正确」的代理证据；而 AC 的真实落点在 UI 层，**该脚本一条 UI 断言都没有**。

### ③ `verify_waveC2` —— 导出装配器用「脚本内复刻」，从不触达真方法

```dart
// app/lib/ui/export_backup_page.dart:126
includeDraft: true,   →   includeDraft: false,
```
**重跑：48 通过 / 0 失败（全绿）**

根因：脚本 §2/§3 用的是**脚本内逐字复刻**的 `buildBackup()`（`verify_waveC2.dart:94-111`），**从不调用真的 `_buildBackupData`**。⇒ 真方法现状与复刻体一旦漂移，脚本**静默失去意义**。

### ④ `verify_waveD1` —— P09 规则编辑页的写库分支可整体对调

```dart

// app/lib/ui/rule_edit_page.dart:349

```
**两次重跑均：65 通过 / 0 失败（全绿）**

意义：P09 是「节假日倍率配成 3.0 能不能生效」这条链路的**用户入口**，而它的真实分支**无凭据**。

### ⑤ `verify_db` G4 —— M-03 当年专门修的「不安全兜底方向」无断言守着

```dart
// app/lib/db/database.dart:1640
RecordStatus.draft;   →   RecordStatus.confirmed;
```
**重跑：93 通过 / 0 失败（全绿）**

`_recordStatus` 把无法识别的状态兜底为 `draft`（安全方向，M-03 从 `confirmed` 纠正而来）。但脚本**从未插入过脏状态行**，改回 `confirmed` 后（脏行计入应收 → 剩余虚增）**依然全绿** —— 修复本身没有回归网。

### ⑥ `verify_waveB` —— 「注释救活」

```dart

includeDraft: false,   →   includeDraft: true,     （违反 AC-32）
```
**重跑：76 通过 / 0 失败（全绿）**

根因：`verify_waveB.dart:683` 用 `p03.contains('includeDraft: false')`，而 `calendar_page.dart:12`/`:78` 的**文档注释里存在同一字面量** ⇒ 改代码后断言被注释救活。§5 对 p03/p04 **不剥注释**。

### ⑦ `verify_core` —— 子串包含 + 删列全盲


## 七、结论：可信度分级与边界声明

### 7.1 按「全绿能支撑什么」分级

| 级别 | 脚本 | 全绿可以支撑 |
|---|---|---|
| **A · 可信** | `verify_waveD2` | 「D2 的入口接线与死路由处置正确」**可以作为凭据** |
| **B · 分层可信** | `verify_db`（B+）、`verify_core`（中高）、`verify_waveA`（数据层部分） | 「**行为层所覆盖的** DB / 引擎 / day_context 链路正确」。**不可**外推为「页面口径正确」「表结构正确」 |
| **C · 部分可信** | `verify_waveB`（行为层）、`verify_waveC2`（DB/SDK 驱动部分） | 同上，且**静态文本层部分需逐条查分册** |
| **D · 弱** | `verify_waveA2`、`verify_waveD1` 的静态层、`verify_waveC2` 的 UI 装配 | **不足以支撑任何交付面结论** |

### 7.2 三句必须一起引用的边界声明

1. **「DB Schema 全绿」≠ 表结构正确** —— 子串匹配 + 不校验列/类型/约束（删核心金额列仍全绿）。
2. **「页面口径全绿」不存在** —— Wave A/B/C2/D1 的用户可见口径**没有任何断言守着**；`verify_waveA`/`waveA2` 的「全绿」不能支撑 `AC-P01-*` / `AC-PDBT-*` / `AC-P06-*` / `AC-P07-*` 的验收结论。
3. **sha256 断言是变更看门狗，不是质量证据** —— 它的绿只能说明「文件没被碰」，不能说明「行为对」。

### 7.3 一个正面结论（同样重要）

**`impl-d1c` 对 `verify_waveD1` 的加固是真实有效的**：注入 `quick_add_sheet.dart:254` 单分支 `ctx.isHoliday→ctx.isWeekend`、`:343` status 三元式对调，**均实测置红** ⇒ `review-d1b` 的 MAJ-2 确已闭合。
**但仍抓不住「取值来源算错」**：`quick_add_sheet.dart:172` 把 `workDate: _workDate` 改成 `DateTime.now()` ⇒ **65/0 全绿**。
