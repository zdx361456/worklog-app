## 方法（3 条，够复核即可）

1. **抽取口径**：`01`~`05` 里凡被标为「覆盖缺口 / 未覆盖 / 部分覆盖 / AC 零断言 / G-N / Gn / S1-S2」的登记点，全部抽出；同一缺陷跨分册重复只合并 1 处（`02:420` 的护栏行与 `04:431` 的 `G-6` 是同一对象，合并为 `GAP-16`）。
2. **判定口径**（五值之一，不设中间态）：
   - `已补`：能指出脚本 + 行号 + 断言原文，并说明「实现怎样坏会红」；
   - `未补`：找不到可证伪断言，或断言**写宽了**（阈值、名实不副）；
   - `[真机]档不在静态覆盖内`：剩余子句本质是渲染 / 手势 / 弹窗 / 平台 FS，且分册或 AC 定义已标 `[真机]`；
   - `结构性不可达`：不改 `app/lib/**` 无法构造验证；
   - `未核实`：本表未核到（本表为 0）。
3. **证据级**：本次亲跑了 10 个脚本，基线全绿（`core 104/0`、`db 117/0`、`p01 exit=0`、`waveA 69/0`、`waveA2 39/0`、`waveB 78/0`、`waveC2 72/0`、`waveD1 74/0`、`waveD2 41/0`）。但按主理人裁示——**「断言存在且当前通过」不等于「缺口已闭环」**——主表证据级一律按**对该条判定的实际证据**标注：本轮未做注入，故除 `GAP-03`（脚本直接打印 q5/q6 行为观测）记 `【实测】` 外，其余全部 `【读码】`；引用 `06` 置红处均在「依据」列注明「06 注入」。

### 口径统一说明（为什么是 55 而不是 ≈38）

`00:93` 已自认各分册口径不同。复算：按 `00` 表字面数相加 = **42**（waveA 取 9）；waveA 取"约14" = **47**；声称 **≈38**。三者互不相等，说明 ≈38 是估算口号。差额来自：

| 原报告漏计项 | 条数 |
|---|---|
| `db` 的 `S1/S2`（合并）+ `_assertSnapshotUnchanged` 护栏 | +2 |
| `waveA` 并集（20）比"约14"多（`03` §4.1 与 §5.3 两份 AC 清单互斥，并集 20） | +6 |
| `waveC2` 记"6 项"，最后一行实含 `AC-P13-05` 与 `AC-P13-06` 两个 AC | +1 |
| `06` 追加的缺口类（`waveC2-B`、`R-83`） | +2 |
| 其余无法从任何分册复算 | +6 |
| **合计** | **+17（38→55）** |

> 本表与 **34 处假覆盖**是两个账本：其中 25 条与 34 条里的 25 个注入点同源，但**不合并计数**；34/34 的闭环结论以 `06` 为准，本表只转述。

### 7.2 GAP-19 为什么只能做到「静态代理」

`aggregateByCompany()` **无 `ledgerId` 参数**（`database.dart:333`），`aggregate(null)` 同样是**全账本**聚合。
因此**在同一进程 / 同一数据库文件内无法造出「0 家公司」的隔离夹具**——新建一个空账本不会让
`aggregateByCompany()` 返回空。要真测，需要**第二个 DB 文件**（新 `AppDatabase` 实例）或真机上删光公司。

如实登记：**GAP-19 的「真 0 家 / 真 1 家」行为边界，归入真机档**（与 GAP-18/31/51/52 并列）。
