## 4. 独立重算结果（维度 B · 不采信自证）

> 重算口径（全产品唯一算法，PRD §2.9 / §4.4）：`剩余 = 应收总额 − 已收总额 − 借支未还`，其中 `借支未还 = Σ借出 − Σ归还`；`期结余 = 该期应收 − 该期已收 − 该期借支净额`。

### 4.1 AC-52 / AC-52b 数值链 —— 与 PM 结论**一致**

| 记法 | 应收 | 已收 | 借出 | 归还 | 期结余 | 公司剩余 | 与 PM |
|------|------|------|------|------|--------|---------|-------|
| AC-52 推荐 | 5000 | 5000 | 1000 | 1000 | 5000−5000−(1000−1000)=**0** | 5000−5000−0=**0** | ✅一致 |
| AC-52b 等价 | 5000 | 4000 | 1000 | 0 | 5000−4000−(1000−0)=**0** | 5000−4000−1000=**0** | ✅一致 |

**结论**：两种记法**结果确实都等于 0**，差别仅在"借支未还"是否仍挂 1000。✔ 无异议。

### 4.2 AC-55 跨周期借支 —— 与 PM 结论**一致**

- 7 月期：借出自动归 7 月期。`期结余(7月) = 0 − 0 − (1000−0) = −1000`（"本期净预支"）✔
- 8 月期：`期结余(8月) = 5000 − 5000 − (0−1000) = +1000`（"本期净归还/抵回"）✔
- **Σ = −1000 + 1000 = 0**；公司剩余 `= (0+5000) − (0+5000) − (1000−1000) = 0`。**Σ = 公司剩余 = 0 成立** ✔

**结论**：AC-55 数值链成立。✔ 无异议（注：7 月期"无应收"仍成立，因借出/归还分别归两期，抵消）。

### 4.3 AC-57 三种记法 —— 与 Dev 结论**一致**

| 记法 | 算式 | 结果 | Dev 声称 | 核对 |
|------|------|------|---------|------|
| ① 归还 1000 + 收款 5000 | 5000−5000−(1000−1000) | **0** | 0 ✅ | ✔ |
| ② 不记归还 + 收款 4000 | 5000−4000−(1000−0) | **0** | 0 ✅ | ✔ |
| ③ 归还 1000 + 收款 4000 | 5000−4000−(1000−1000) | **1000** | 1000 ✅ | ✔ |

**反例独立复现**：若这 1000 是**用户自掏腰包归还**、老板只**另付部分款 4000**（尚欠 1000）→ 正确剩余 `= 5000−4000−0 = 1000`，**③ 恰好正确** ✔。
**结论**：Dev 关于"③ 并非在任何场景都错、系统运行时无法自动判错"的论断**成立**；AC-57「可据此判定混用」的措辞确实**不严谨**。详见第 5 节 C-4。

**结论（限定条件）**：
1. **"必现失败"这一定性成立**——只要 D_old ≠ D_new，新旧边界几乎不可能恰好对齐（需 `新起点 = 旧结束+1`），因此**变更边界处必然产生"重叠"或"空洞"之一**，二者都破 AC-56。✔ 确认。
2. **但 Dev 举例的区间 `9/6–9/15` 与 PRD 自身约定不一致**：按 PRD `[20→19]` 推 D=15 → `[15, 14]`，重叠应为 `9/5–9/14`，而非 `9/6–9/15`。**说明"周期闭合边界口径"（结算日当天算哪一期）PRD 全局未定义**——这本身是第 6 节 S-07 的新发现。
3. **⚠️ 最严重的新发现：Dev 给出的修复方案（03 §6.2 切换点钳制）自身不完备**——见下。

**对 Dev 修复算法的独立反例（Dev 未察觉）**：
`03 §6.2` 定义 `切换点 = max(新配置首个 ≥ t 的周期起点, 最后旧周期结束日 + 1)`。
- 当"新起点 < 旧结束+1"（上表 t=9/1、9/5）：钳制**向上**，正确答案，但会在新配置下产生一个**非自然边界**的短周期（可接受）。
- 当"**新起点 > 旧结束+1**"（上表 t=9/10、9/14）：`max` 取到的是**新起点 10/5**，钳制**不起作用 → 留下空洞 [9/15, 10/4]**；Dev 的 §6.2 第 4 步"用旧配置补齐 [缺口 → 切换点)"会生成旧配置周期 `[9/15, 10/14]`，其 `10/14 > 10/5` → **与新区间再次重叠**。
- **即：Dev 的钳制算法在"新起点晚于旧结束+1"时，要么留空洞、要么造重叠——G2（MECE）仍不成立。** 这是 `04 §0` 所称"唯一必现缺陷"的**修复方案本身仍有缺口**，必须重新设计（建议：切换点强制取 `旧结束+1`，并以该日为新配置的**首个非自然起点**，后续周期从该起点滚动，避免用旧配置补齐跨越切换点）。

### C-2 恒等条件 G1–G4 是否完备 → **不完备，确认遗漏 3 条**

对 `Σ_p 期结余(p) = 口径A` 独立推导：`Σ_p[应收(p) − 已收(p) − 借支净额(p)] = Σ_p应收(p) − Σ_p已收(p) − Σ_p借支净额(p)`，故只需各分项**分区求和 = 直接求和**。在此框架下，G1–G4 是**充分**条件，但**遗漏以下使恒等不成立的场景**（均为本报告独立构造，Dev 未列）：

- **N1（G1 未覆盖·函数不良定义）**：默认归期策略"**最早未结清周期**"存在**循环依赖**——`归期(归还)` 依赖"未结清"，而"未结清"由 `期结余` 判定，`期结余` 又依赖 `归期(归还)`。G1 只要求"返回恰一期"，**未要求函数良定义（无自引用/求值时点明确）**。若实现按"含本笔/不含本笔"不同求值时点，**同一输入可得不同周期**，Σ 可能 ≠ 口径A。→ **必须补：明确"未结清"的求值时点（不含待归集归还本身）+ 定义"净预支期"是否算未结清**。
- **N2（G1/G2 未覆盖·跨公司引用）**：`PaymentRecord.offset_period_id` / `AdvanceRecord.offset_period_id` 仅约束"可空外键"，**未约束"该周期必须属于本公司"**。若该外键指向**别的公司的周期实例**（误操作或 bug），本公司口径B 会**漏计**该笔 → 破恒等。G1 只保证"恰好归一期"，未保证"归本公司域内的期"。→ **应补约束：`offset_period_id.company_id == record.company_id`**。
- **N3（C1 对策与 04 §2-1-6 冲突·内部矛盾）**：`03 §5.3-C1` 的对策是"归期遇空 → **强制懒生成**"（即任何日期都可生成周期）；而 `04 §2-1-6` 又建议"设**账本建立日**为生成下界"。**二者互相矛盾**：一旦设下界，"早于建账日的补记"就无法生成周期 → **C1 空洞必现，且 C1 对策失效**。→ **必须先裁定"是否存在建账前补记"（V1），二者只能取其一**。

> **提示**：Dev 在 `03 §13` 写"当且仅当…"属**过强表述**（G1–G4 是充分非必要）；不影响结论，但建议改为"当…时必然成立"。

### C-4 AC-57 措辞修正 —— **更严谨，不削弱保护；建议采纳并补第三方案**

- **更严谨**：✔。已由 C-1 反例证明——同一组记录（③）在"扣工资"场景错、在"自掏腰包+部分收款"场景对，**运行时系统无法区分真实意图**。原措辞"可据此判定混用"会被误读为"系统能自动判错"，**制造虚假保护**。
- **是否削弱对用户保护**：**否**——系统**本就不具备**自动判错能力，修正只是**去掉虚假承诺**，实际能力不变。
- **第三方案（建议采纳）**：把"判定"降级为**"带条件的启发式提示"**，兼顾诚实与可用性：
  > AC-57 改为：「**不承诺运行时自动判错**。仅**测试（ground truth）**可对照验证 ①②③ 的数值关系；运行时**仅提供启发式提示**（触发条件：`收款额 + 归还额 ≈ 该期应收` → 标注"疑似从工资扣款，请核对收款是否为应发全额"），且提示**不阻断保存、明示不确定性**。」
  > 此方案与 `04 §2-3` 已列的第 2 类提示一致，只需把它正式写进 AC-57 与 §4.4。
