## 〇、定案结论（先看这个）

**基础版技术栈定案：Flutter + Dart + SQLite（drift/sqflite）**

- 数据：SQLite 存手机本地，**不依托任何第三方平台**，断网可用，账目只在用户自己手里
- 后端：**不需要**（一期零后端）；二期做云备份/多端同步时再加 Supabase 类轻后端
- 导出备份：生成 JSON（全量恢复）+ CSV（人读），写入手机存储 / 调系统分享
- 分发：安卓先打 apk 私下装 / 后续上架应用商店

**选型理由**（对应用户三个回答）：
1. 安卓为主 → Flutter 安卓端成熟、体验好
2. 要「彻底独立、不依托微信/浏览器」→ 只有原生 App 满足（小程序依托微信、PWA 依托浏览器，均已排除）
3. 分享暂不做 → 无需云端，纯本地自洽

## 一、先把一个误区说清楚

## 一、先把一个误区说清楚

用户的核心疑问是：「本地库是不是得靠本地安装？PWA 是不是只能通过浏览器访问、做不到手机操作？有没有不需要服务底座的方式？」

**结论先行**：

1. **「不需要服务底座」三条路都能满足**——本地数据库（SQLite / IndexedDB / 小程序缓存）都不需要后端服务器，数据只存在手机里。**后端服务这件事，一期三种方案都不需要。**
2. **「是不是真 App」才是三条路的真正区别**：
   - **原生 App** = 真·独立安装的应用（数据存手机 SQLite）
   - **PWA** = 浏览器套壳，点「添加到主屏幕」后**看起来**像 App（数据存手机浏览器 IndexedDB）
   - **小程序** = 微信内的应用（数据存微信本地缓存）
3. 所以「本地库」不是问题——**问题只有「要不要真 App」**。

## 二、三方案总览

| 维度 | 原生 App（Flutter） | PWA 网页应用（Vue/React） | 微信小程序 |
|------|--------------------|--------------------------|-----------|
| 本质 | 独立安装包 | 浏览器套壳 | 微信内应用 |
| 打开方式 | 桌面图标直接开 | 加到主屏幕后点图标开 | 微信里下拉/扫码开 |
| 离线可用 | ✅ 完全 | ✅ 完全 | ✅ 基本 |
| 本地数据 | SQLite（真文件） | IndexedDB（浏览器内） | 小程序本地缓存 |
| 需要后端吗 | 一期不需要 | 一期不需要 | 一期基本不需要 |
| 导出备份 | ✅ 可导出文件到手机 | ✅ 下载文件 | ⚠️ 受小程序能力限制 |
| 分享给工友 | 各装各的 App | 发链接各打开 | 发小程序码 |
| 上架分发 | 应用商店 / 安装包 | 免上架（发网址） | 微信审核 |

## 三、逐条深入对比

### 3.1 开发成本与周期（从零到基础版可用）

| 方案 | 技术栈 | 环境要求 | 预估上手门槛 | 周期相对值 |
|------|--------|---------|-------------|-----------|
| PWA | Vue3 / React + TS + IndexedDB | 只需 Node.js | **最低** | 快（1.0×） |
| 原生 App | Flutter + Dart + SQLite | Flutter SDK + Android/iOS 工具链 | 高 | 慢（1.5–2×） |
| 小程序 | 原生小程序语法 + 云/本地缓存 | 微信开发者工具 + 小程序主体 | 中 | 中（1.2–1.5×） |

**关键点**：PWA 用网页技术，浏览器打开即调试，不需要模拟器/真机环境就能看效果；Flutter 需要装整套工具链，且要打包成 apk 才能在手机上看。

### 3.2 你的「手机操作」诉求能否满足

三条路**都能在手机上操作**，差别在「质感」：

- **原生 App**：最顺滑、启动最快、手势最跟手，是真正的「手机软件」体验。
- **PWA**：日常操作（点按、翻日历、填表）体验已经很接近 App；但在弱信号下首次加载、以及个别安卓机型上，偶有「不像原生」的细微感。
- **小程序**：体验居中，但受微信框架约束（如转发、文件导出不如原生灵活）。

> 对「收工随手记」这个高频、快操作场景，三者的日常体验差距其实不大；差距主要体现在「首屏启动速度」和「极致顺滑度」上，原生最好。

### 3.3 数据本地 + 导出备份（你的硬需求）

| 方案 | 本地存储能力 | 导出备份实现 | 备份文件去哪 |
|------|-------------|-------------|-------------|
| PWA | IndexedDB，容量大、结构化好 | 一键生成 JSON/CSV 触发浏览器下载 | 手机「下载」文件夹 |
| 原生 App | SQLite，最稳、可索引 | 生成文件写入手机存储 / 调系统分享 | 手机任意目录/微信等 |
| 小程序 | 本地缓存有**容量上限**（约 10MB） | 导出受限制，需借助「保存到相册」或引导复制 | 受限 |

> **这里有一个对 PWA 的提醒**：浏览器 IndexedDB 的持久性在个别极端情况下（如用户清理浏览器数据、系统空间告急）**可能被清掉**。所以 PWA 的「导出备份」不只是锦上添花，而是**必须养成习惯的兜底手段**——好在你要的基础版已经把它列为 P0（D6）。
> 原生 App 的 SQLite 则不存在「被浏览器清理」的隐患，数据更「踏实」。

### 3.4 分发与「分享给工友」

- **原生 App**：要上架（苹果要审核+年费，安卓可发 apk）；工友装起来最「正规」，但门槛也最高。
- **PWA**：发一个网址，工友浏览器打开、加到主屏幕即可用，**零门槛**；但苹果 iOS 对 PWA 的「加到主屏幕」体验略打折扣。
- **小程序**：微信扫码/搜索即用，**分发最轻**；但你要有注册过的小程序主体，且数据导出受限制。

### 3.5 二期演进（云备份 / 多端同步 / 账目分享）

- 三条路二期都要加「本地优先 + 可选云」：上一个轻后端（如 Supabase 托管：数据库 + 文件存储 + 登录）。
- **PWA 和原生 App 接云都很自然**；小程序接云更受微信云开发约束。
- 一期本地、二期加云，三者架构都能平滑演进，**不因选型锁死**。

## 五、推荐与理由

### 推荐：一期用 **PWA**，验证顺手后二期再决定是否包成原生 App

**理由**（按你的场景逐条对应）：

1. **你还在「验证想法」阶段**——基础版刚做完设计，最需要的是「快点用起来、看看记工流程顺不顺手」。PWA 开发最快、免安装、今天做完明天就能在手机上点开用。
2. **数据全本地这点 PWA 满足**——IndexedDB 存手机浏览器里，离线可用，不违背你的底线。
3. **导出备份正好是 PWA 的强项**——一键下载 JSON/CSV，正好对冲它「可能被清数据」的唯一短板。
4. **代码可平移**——PWA 的核心逻辑（数据模型、金额引擎、剩余算法）是纯 TypeScript，将来要包成原生 App（Flutter）或加云后端，这些逻辑几乎原样复用，**不会白做**。
5. **后端服务**：一期完全不需要；二期做云备份时再上 Supabase 类轻后端。

### 什么时候改选原生 App（Flutter）

当出现以下任一信号时，从 PWA 迁到 Flutter：
- 你决定要**正式上架应用商店**；
- 你或工友**大量使用 iPhone** 且对 PWA 体验不满意；
- 账目量大了、对「数据绝对安全不被浏览器清理」有强诉求。

> 届时迁移成本可控：数据模型和算法复用，主要重写 UI 层。

### 7.4 数据访问层的依赖边界（2026-09-30 实施决策）

> **背景**：实施阶段发现「数据层无法脱离 Flutter 做运行时验证」，据此调整了 `db/` 的依赖边界。
> 本决策经主理人独立核验并接受（2026-09-30）。
> **归属说明**：本决策属技术选型，故落在本文档；`03-数据模型与信息架构.md` 按自身 §0 约定
> 保持「不落技术选型」，仅在其 §6.6 留一行指针。

**决策**：数据访问层只依赖 `package:sqflite_common`，**不** import `package:sqflite`。

| 项 | 结论 | 证据（文件:行号 / 包内路径） |
|---|---|---|
| 数据层 import | `package:sqflite_common/sqflite.dart` | `app/lib/db/database.dart:43` |
| 决策与理由（代码内落档） | 类头「6. 可移植性纪律」 | `app/lib/db/database.dart:22-30` |
| 依赖声明 | `sqflite: ^2.4.4`（**必须保留**）、`sqflite_common: ^2.5.13` 为 direct **main**；`sqflite_common_ffi: ^2.3.4` 为 direct **dev**（仅纯 Dart 验证脚手架用，不进 Android 包体） | `app/pubspec.yaml:41` / `:48` / `:56` |

**为什么必须这样分（硬约束，非偏好）**：
`package:sqflite/sqflite.dart` → `package:flutter/foundation.dart` → `dart:ui`，
而 `dart:ui` **在纯 Dart VM 下不可用**（实测）：
```
Error: Dart library 'dart:ui' is not available on this platform.
```
→ 若保留 `package:sqflite`，`dart run tool/verify_db.dart` 在原理上不可能成功，
数据层将永远拿不到运行级证据。

**平台 factory 注入链（已核源，逐跳可查）**：
1. `sqflite_android-2.4.4/pubspec.yaml:30` → `dartPluginClass: SqfliteAndroid`
2. `sqflite_android-2.4.4/lib/sqflite_android.dart:8-9` → `registerWith() { SqflitePlatform.initWithDatabaseFactoryMethodChannel(); }`
3. `sqflite_platform_interface-2.4.2/lib/sqflite_platform_interface.dart:15` → `impl.databaseFactoryOrNull ??= SqflitePlatform.databaseFactoryMethodChannel;`

→ Flutter 构建时生成的 Dart plugin registrant 会自动调用 `registerWith()`，
因此**不 import `package:sqflite` 也能拿到默认 factory**，Android / iOS / macOS 链路无破坏。
（注：`sqflite-2.4.4/pubspec.yaml` 本身没有 `dartPluginClass`，注册发生在
`sqflite_android` / `sqflite_darwin` 这层平台实现包。）

**使用约束（务必遵守）**：
- **`sqflite` 必须保留为 direct 依赖，不得删除** —— 删掉会使 Android 侧插件注册消失，`databaseFactory` 变 null。
- **应用交付目标为 Android**：默认 factory 由平台插件（`sqflite_android`）自动注入，**无需手动注入**；
  手动注入 `databaseFactory = databaseFactoryFfi;` **仅在纯 Dart 验证脚手架**需要
  （`tool/verify_db.dart` 即此模式）。
- ~~Windows / Linux 端须显式注入 ffi factory~~ —— **该约束已撤销**：桌面端**非交付目标**
  （依据 `01-需求理解与边界.md:39` D3「手机为主」、`02-PRD.md:61`「手机端为主」；桌面小组件属
  **三期候选**，`02-PRD.md:229`）。故不再作为运行时约束（见 00 台账 I-7「已撤销·不在范围」）。
- 本层不 import Flutter 是「数据层可独立验证」的前提；上层（UI / bootstrap）不得反向要求本层 import Flutter。
