## 2. 基础版重点风险审查（v2 新增）

### 2-1 导出 / 导入数据完整性

| 风险点 | 判断 | 对策（03 §6） |
|--------|------|--------------|
| 快照被重算（导入后金额变了） | 真实风险——若导入走"重算"而非"原样写入"，即破底线 2 | 导入 = **原样 upsert**（id/快照结构不重编码）；`assertExportConsistency` 断言"导出合计 = App 合计"（定点相等） |
| 金额精度损失（浮点序列化） | 真实风险——JSON number 走浮点会丢分 | 备份金额以**整数分**序列化（03 §6.2）`[待验证]`：实现期复核定点层↔整数分换算 |
| id 冲突（换机/重复导入） | 必现场景 | 三选策略 + 推荐"覆盖 + 导入前自动备份"（03 §6.4） |
| 半成品写入（导入中途失败） | 真实风险 | 单事务全成或全回滚（03 §8-13） |
| 坏文件 / 旧版本文件 | 真实风险 | `schema_version` 门禁 + 结构校验硬拒绝（03 §6.4）；未知版本提示升级 App |
| CSV 当导入格式（快照结构损失） | 误用风险 | **CSV 仅导出查看，不作为导入格式**；导入仅接受 JSON |

**结论**：可实现；完整性靠"断言 + 事务 + 门禁"三件套保证，测试期必须全量跑（AC-60~64 建议，03 §10-3）。

### 2-2 大记录量下手机端统计性能

- 量级评估：个人账本年记录 10³ 量级（场景 C 高频计件按每天 8 条、全年无休 ≈ 3000 条/年，5 年 ≤ 1.5 万条）。
- 派生查询 O(当月/当期记录数)，月历/看板在手机端**可接受** `[待验证]`：实现期用 5 万条 mock 数据实测日历/统计/导出耗时，超标再加可重建缓存（03 §7.2）。
- 导出全量序列化 1.5 万条 JSON：手机端秒级 `[待验证]`：同上实测；若慢，导出走后台任务 + 进度条。

### 2-3 跨夜 / 多段边界

v1 判断**继续成立**（Reviewer 复核无异议）：可实现。边界集中在——
- 起止时间结束 < 开始且未开跨夜：提示"是否跨夜？"，不静默算负数（AC-11）；
- 跨夜默认归开始日、可改结束日（AC-08~10）；跨夜跨月归属明确（AC-09）；
- 一天多段不同单价 = 多条记录，各自快照（Q2 已决）。
- 实现方案见 03 §4.4。

### 2-4 借支后移的过渡期口径失真（**诚实标注，按纪律写出，不沉默执行**）

**风险**：用户范围裁剪把借支整体后移二期，但**用户的现实借款不会因此消失**。基础版 `剩余 = 应收 − 已收`，对"已借未还"的用户会**把已借的钱当作仍会拿到 → 剩余虚高**。

| 项 | 判断 |
|----|------|
| 严重度 | **中**——不破数据（显示语义少了借支项），无数据丢失 |
| 影响 | 有借款的用户对账结论偏差；无借款用户（预期多数）完全正确 |
| 对策 | ① 产品明示边界（首启引导/关于页）② 借支以备注/收款暂记，**不建正式字段**（防与二期 AdvanceRecord schema 冲突）③ 二期迁移无结构冲突（AdvanceRecord 为新增表，03 §9.1） |
| 状态 | `[待用户确认]`：目标用户过渡期借支普遍度——若普遍，建议产品文案强化，或评估二期借支模块提前 |
